Real-time Chat Engine

An event-driven messaging backend: Go WebSocket gateways for live connections, Kafka as the message backbone, and MongoDB for history. Designed so messages arrive instantly, in order, and are never lost, even while servers scale up, restart or fail.

Message lifecycle

What happens when you press send

Each step is independent, so a slow database or a busy notification service never slows down live chat.

  1. ConnectThe app opens a WebSocket to a gateway with a short-lived JWT from the Auth API. The gateway checks it once at the handshake and records in Redis which gateway the user is connected to.
  2. SendThe client sends the message with its own unique client_msg_id. The gateway checks the user belongs to the conversation, applies rate limits, and publishes it to chat.messages keyed by conversation_id.
  3. AcknowledgeOnly after Kafka confirms the write (replicated, acks=all) does the gateway reply "sent" to the client. If anything fails before that, the client simply retries with the same ID.
  4. RouteThe router worker looks up where each recipient is connected and publishes to chat.delivery for those gateways; recipients who are offline are handed to the notification worker for a push notification.
  5. DeliverEach gateway consumes its deliveries and pushes them down the right sockets. The recipient's app sends back "delivered" and later "read" on chat.receipts.
  6. StoreIn parallel, the persistence worker writes messages to MongoDB in batches, using client_msg_id so a retried message is stored exactly once.
Event design

Kafka topics

Partition keys are chosen so ordering is guaranteed exactly where it matters.

TopicKeyConsumersWhy it's built this way
chat.messagesconversation_idrouter, persistenceSame key → same partition → messages in a conversation stay in order, while different conversations are processed in parallel.
chat.deliverygateway_idgatewaysEach gateway reads only what it needs to push, so adding gateways spreads the load evenly.
chat.receiptsconversation_idrouter, persistenceDelivered/read ticks follow the same ordering as the messages they refer to.
chat.eventsconversation_idgatewaysTyping and presence are short-lived, with short retention, never stored as history.
chat.dlqoriginal keyalerts, replayAnything that fails repeatedly is parked here for inspection and replay instead of blocking the stream.
Design decisions

Why it's built this way

Each choice trades a little complexity for a lot of reliability.

Language

Go for the gateways

Goroutines make tens of thousands of open sockets cheap. Each connection gets a reader and a writer goroutine with a bounded send buffer, so one slow client can never block the others; if its buffer fills, that client is disconnected and resumes cleanly.

Backbone

Kafka between everything

Services never call each other directly. Kafka absorbs traffic spikes, keeps messages if a worker is down, and lets new features (search, moderation, analytics) be added later as new consumers without touching the gateways.

Guarantees

At-least-once, stored exactly once

Producers retry until Kafka confirms; consumers commit offsets only after their work is done. Duplicates that this can create are removed using the client's message ID, which the database enforces as unique.

Reconnects

Resume, don't reload

When a phone switches networks, the app reconnects and sends the last message ID it saw. The gateway fills the gap from history first, then switches to live delivery, so nothing is missed and nothing is shown twice.

Storage

MongoDB for history

Messages are documents indexed by conversation and time, read with cursor-based pagination ("load older") that stays fast however long a chat gets. User accounts and memberships live in PostgreSQL behind the Auth API.

Security

Checked at every hop

TLS everywhere, JWT verified at the socket handshake, origin checks, membership checked on every send, per-user rate limits and message size limits at the gateway.

Operations

Built to run, not just to demo

Scale by adding instances

Gateways are stateless and workers use Kafka consumer groups, so capacity grows by running more containers behind the load balancer.

Graceful restarts

On deploy, a gateway stops taking new connections, tells clients to reconnect elsewhere and drains its buffers, so releases cause no lost messages.

Observable

Health checks, metrics for connections, consumer lag and delivery latency, and structured logs carrying the message ID end to end.
